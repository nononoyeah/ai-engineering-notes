# Design

## Context

当前项目已完成基础目录初始化，`backend`、`tests` 等目录尚无实际代码。项目使用 Python 作为主要开发语言，本次设计以独立、轻量的文档解析模块为基础，不依赖尚未建立的 Web 服务或 Agent 框架。

本设计对应的功能需求见 `openspec/changes/implement-pdf-document-parser/specs/document-parsing/spec.md`，变更动机见 `proposal.md`。

当前需要考虑的主要约束：

- 优先采用成熟、轻量的 Python 库，避免引入不必要的框架。
- 保留 PDF 原始页序和页码，便于后续文本分块及溯源。
- TXT 和 JSON 使用 UTF-8 编码，保证中文内容能够正确保存。
- 解析逻辑与文件输出逻辑分离，便于后续被 API 或其他模块复用。
- 本阶段不依赖数据库、模型服务或外部网络服务。

## Goals / Non-Goals

**Goals:**

- 建立职责清晰、可独立测试的 PDF 解析模块。
- 统一逐页解析结果的数据结构，为后续文本处理提供稳定输入。
- 将文本提取、文本清洗和文件输出拆分为独立职责。
- 通过自动化测试覆盖正常解析、空白页、无有效文本和异常文件等情况。

**Non-Goals:**

- 不在本阶段建设 Web API、前端页面或文件上传服务。
- 不实现扫描版 PDF 的 OCR。
- 不实现文本分块、Embedding、向量检索和大模型问答。
- 不引入 LangChain、LangGraph 等 Agent 开发框架。
- 不建设数据库存储和任务队列。

## Decisions

### 1. 使用 Python 作为实现语言

**决定：** 使用 Python 实现文档解析模块。

**原因：**

- Python 具有成熟的 PDF 文本处理生态。
- 与后续计划中的文本分块、Embedding 和 RAG 流程衔接自然。
- 本阶段无需引入独立的 Java 或 Go 服务，降低项目初期复杂度。

**备选方案：**

- Java：也能完成 PDF 解析，但当前阶段引入 Java 技术栈没有明显收益。
- Node.js：用户具备 JavaScript 基础，但 Python 在后续 AI 文本处理环节的生态更适合本项目。

### 2. 使用 PyMuPDF 提取 PDF 文本

**决定：** 使用 PyMuPDF（`fitz`）读取 PDF 并提取页面文本。

**原因：**

- 支持读取 PDF 文件和逐页提取文本。
- 可以直接获取页面数量及页面顺序。
- 接口相对简单，适合当前独立解析模块。
- 能满足本阶段以文本型 PDF 为主的解析需求。

**备选方案：**

- pypdf：同样可以提取 PDF 文本，但本阶段优先选择 PyMuPDF 的页面文本提取能力。
- pdfplumber：提供更丰富的版面和表格处理能力，但当前需求暂时不需要这些能力。

本阶段不进行 OCR。对于只有图像、无法提取文本的 PDF，明确报告没有可提取的文本内容。

### 3. 将解析流程拆分为独立模块

**决定：** 采用小规模模块化设计，避免把 PDF 读取、清洗和文件写入全部放在一个函数中。

建议目录结构：

```text
knowledge-assistant/
├── backend/
│   ├── app/
│   │   ├── __init__.py
│   │   └── document_parser/
│   │       ├── __init__.py
│   │       ├── pdf_parser.py
│   │       ├── text_cleaner.py
│   │       ├── exporters.py
│   │       └── models.py
│   └── requirements.txt
├── tests/
│   └── test_pdf_parser.py
└── output/
```

模块职责：

| 模块 | 职责 |
|---|---|
| `pdf_parser.py` | 检查并读取 PDF，逐页提取文本 |
| `text_cleaner.py` | 清理多余空白，尽可能保留段落和列表结构 |
| `exporters.py` | 将解析结果输出为 TXT 和 JSON |
| `models.py` | 定义统一的解析结果数据结构 |
| `test_pdf_parser.py` | 验证解析、清洗、输出和异常处理 |

本阶段采用可直接调用的 Python 模块，不建设 Web API。后续如需增加 API，可以在模块外增加服务层，不需要重写解析逻辑。

### 4. 统一逐页解析结果的数据结构

**决定：** 解析结果以文档级对象组织，包含文件名、总页数和逐页内容。

建议数据结构：

```json
{
  "filename": "example.pdf",
  "total_pages": 2,
  "pages": [
    {
      "page_number": 1,
      "text": "第一页提取的文本内容"
    },
    {
      "page_number": 2,
      "text": "第二页提取的文本内容"
    }
  ]
}
```

设计约定：

- `filename`：原始 PDF 文件名。
- `total_pages`：PDF 总页数。
- `pages`：按照 PDF 原始页序排列的页面数组。
- `page_number`：从 1 开始计数。
- `text`：完成基础清洗后的页面文本。
- 空白页仍保留对应页面记录，`text` 使用空字符串。

该结构作为解析模块的统一输出，TXT 和 JSON 导出均基于这一结构生成。

### 5. 使用保守的文本清洗策略

**决定：** 使用 Python 标准库实现基础清洗，不引入额外文本处理依赖。

清洗原则：

- 去除文本首尾无意义空白。
- 处理连续空格和多余空行。
- 保留合理的段落换行。
- 尽可能保留列表内容的换行关系。
- 不擅自删除标点、数字或正文内容。
- 不在本阶段进行跨页段落合并。

清洗按页面分别执行，避免破坏原始页码与内容的对应关系。

### 6. TXT 和 JSON 分别承担阅读与结构化用途

**决定：** 两种输出均由同一份解析结果生成。

**JSON：**

- 使用 UTF-8 编码。
- 保留中文，不将中文强制转换为 Unicode 转义序列。
- 保留文件名、总页数和逐页文本。
- 采用缩进格式，方便人工查看和调试。

**TXT：**

- 使用 UTF-8 编码。
- 按照原始页序输出。
- 使用明确的页码分隔标记，例如 `===== 第 1 页 =====`。
- 保留页面之间的边界，避免不同页面内容混在一起。

默认输出到项目根目录下的 `output` 目录。输出文件以原始 PDF 文件名为基础生成同名 `.txt` 和 `.json` 文件。输出目录不存在时自动创建。

### 7. 明确异常处理策略

**决定：** 对文件级异常采用明确失败策略，不返回看似成功的结果。

处理约定：

| 异常场景 | 处理方式 |
|---|---|
| 文件路径不存在 | 返回明确的文件不存在错误 |
| 文件不是有效 PDF | 返回明确的 PDF 格式或解析错误 |
| PDF 无法读取 | 返回明确的读取失败信息 |
| 单页文本提取异常 | 中止本次解析并报告失败，不输出不完整结果 |
| 页面没有可提取文本 | 保留页面记录，文本为空字符串 |
| 所有页面均无可提取文本 | 报告没有可提取文本，不作为成功解析处理 |
| 输出目录创建失败 | 报告输出失败 |
| TXT 或 JSON 写入失败 | 报告输出失败，不将本次导出视为成功 |

导出时先完成解析，再写入文件。尽可能采用临时文件写入后替换目标文件的方式，降低写入中断导致文件不完整的风险。

### 8. 使用 pytest 进行自动化测试

**决定：** 使用 pytest 作为测试框架。

**原因：**

- 适合 Python 项目的模块级和功能级测试。
- 可以清晰组织正常场景与异常场景。
- 能够与后续项目持续集成流程衔接。

测试 PDF 优先在测试过程中动态生成，避免依赖外部真实文档或将含有个人信息的 PDF 提交到 GitHub。

测试至少覆盖：

- 有文本的单页 PDF。
- 有文本的多页 PDF。
- 包含空白页的 PDF。
- 不存在的文件路径。
- 非 PDF 文件。
- 无可提取文本的 PDF。
- 中文文本提取和 JSON 输出。
- TXT 页码顺序及页面分隔。
- 输出目录不存在时的创建行为。
- 页面提取或文件写入异常时的错误处理。

## Risks / Trade-offs

- [PDF 文本布局复杂，提取结果可能与原始排版不同] → 本阶段只保证文本内容和页码顺序，不承诺还原原始版面；清洗策略尽量保留段落和列表换行。
- [扫描版 PDF 无法通过普通文本提取获得正文] → 明确提示没有可提取文本，将 OCR 留到后续独立变更。
- [不同 PDF 文件可能存在字体编码或文本映射问题] → 使用包含中文的测试样例验证基本能力，并在实际使用中记录无法正确提取的样例。
- [过度清洗可能破坏原文结构] → 采用保守清洗策略，不做跨页合并和激进格式转换。
- [大文件可能占用较多内存或处理时间] → 当前 MVP 以常规 PDF 为目标，暂不引入异步任务和流式处理；后续根据实际测试结果优化。
- [依赖版本变化可能影响解析行为] → 在依赖文件中固定经过验证的版本，并通过自动化测试检查升级影响。

## Migration Plan

本次为新项目中的首个 PDF 解析功能，不涉及已有业务数据迁移，也没有线上服务切换。

实施步骤：

1. 建立 Python 依赖文件，安装 PyMuPDF 和 pytest。
2. 创建解析结果数据结构。
3. 实现 PDF 文件读取和逐页文本提取。
4. 实现基础文本清洗。
5. 实现 TXT 和 JSON 导出。
6. 补充正常场景和异常场景测试。
7. 执行自动化测试，验证输出文件和中文内容。
8. 更新项目 README，记录依赖安装、测试和模块调用方法。

回滚策略：

- 本次新增代码均集中在文档解析模块，不修改已有业务模块。
- 如果实现出现问题，可以移除新增解析模块及对应依赖，恢复到本次变更前的项目状态。
- 测试生成的 PDF 和解析输出文件不作为项目源代码提交。

## Open Questions

无。本阶段的技术选型、模块边界、数据结构和异常处理策略已明确，可以进入任务拆分阶段。
